## Approved PDF attachment extension

- Add `resource_attachments` with attachment ID, resource ID, generated storage key, original filename, size in bytes, PDF content type and upload timestamp. Create the table additively with `CREATE TABLE IF NOT EXISTS`; do not reset, recreate or rewrite existing database files or resource rows. Add `attachmentCount` to resource response DTOs so the Resource Library can show persisted attachment totals without per-row requests.
- Store bytes beneath configurable `APP_ATTACHMENT_STORAGE_DIR` (default `data/attachments`) and keep only metadata plus generated UUID storage names in SQLite. Configure a default per-file limit of 20 MiB via `APP_ATTACHMENT_MAX_FILE_SIZE` and return the effective byte limit from `GET /api/attachments/policy`. Use PDFBox to parse and validate uploaded content; sanitize the display filename, keep it separate from the generated storage key, and verify resolved file paths remain inside the configured directory.
- Add SHA-256 content and a unique upload idempotency key to attachment metadata. Create the table additively with `CREATE TABLE IF NOT EXISTS`; if an earlier attachment schema already exists, add only missing columns/indexes without rewriting existing records or files.
- Attachment API: `POST /api/resources/{resourceId}/attachments` accepts one multipart field `file` and an optional UUID `Idempotency-Key`; `GET /api/resources/{resourceId}/attachments` lists metadata; `GET /api/resources/{resourceId}/attachments/{attachmentId}/content` serves an inline `application/pdf`; `GET /api/resources/{resourceId}/attachments/{attachmentId}/download` downloads the file; and `DELETE /api/resources/{resourceId}/attachments/{attachmentId}` removes only that attachment. An identical retry with the same token returns existing metadata without storing another file; reusing the token for different resource/name/content returns 409. Use the existing structured API error format for invalid, oversized, missing, conflicting and unavailable storage cases.
- The browser accepts multiple selections and uploads sequentially, showing per-file and aggregate progress plus clear success/failure states. Each selected file keeps the same UUID idempotency key across retries. The details page lists filenames and sizes, offers a native in-app PDF viewer, switches documents without leaving resource context, and provides download/open-in-new-tab and independent removal. The Library uses `attachmentCount`. Create/edit forms stage new files until metadata save succeeds; on partial upload failure, preserve the resource and successful attachments, navigate to details and let users retry only failed files without duplicating a response-lost success.
- Successful resource detail navigation remains the one counted ID/Splay access. Catalogue searches, attachment-list/content reads, upload/removal, and switching documents do not create successful resource access events. Resource deletion removes attachment metadata transactionally, then safely deletes generated files after commit; upload failures clean up newly written files where possible.
- Tests use isolated temporary SQLite databases and filesystem directories. Preserve the existing API-only default runtime and do not publish/deploy. Hosted container files are not durable unless the configured storage directory maps to persistent storage.

## API integration decisions

Use the verified response DTOs as the frontend TypeScript contract:

- `GET /api/analytics/summary` returns `resourceCount`, `categoryCount`, `totalAccesses`, `treeSize`, `treeHeight`, `popularResources[]`, and `recentResources[]`.
- `GET /api/resources` returns `items`, `page`, `size`, `totalElements`, and `totalPages`; supported list parameters are `q`, `category`, `type`, `page`, `size`, `sort` (`id`, `title`, `createdAt`, `updatedAt`) and `direction` (`asc`/`desc`). The metadata search is case-insensitive across title, description, subject, tags and resource reference. Category and resource type are exact-match filters. There is no standalone subject filter.
- `GET /api/resources/search?q=...` returns the same page DTO, accepts category/type and `limit`, and performs SQL text search rather than Splay Tree search.
- `GET /api/resources/{id}` returns `{resource, search}`. `resource` includes available metadata, timestamps, `sample`, `accessCount`, `lastAccessed` and the additive persisted `attachmentCount`; `search` contains the actual found/comparison/depth/rotation/root metrics. A successful detail open records one access. Browse/search/list/filter/analytics and attachment reads do not. Failed IDs return the backend's actual structured error and do not count as successful accesses.
- `GET /api/resources/popular` returns an array of `{rank, resource}` ranked using recorded access events. `GET /api/resources/recent` returns `{resource, accessedAt}` rows for the bounded distinct-ID tracker history. Label event counts and recent distinct resources accurately; do not imply users or fabricated popularity scores.
- `GET /api/dsa/splay-tree` returns actual node IDs and parent/child links, root, size, height, last accessed ID, latest search and node depth. `/api/dsa/splay-tree/metrics` returns current metrics. The UI may lay out these returned links but must not implement a second tree algorithm or invent rotation-by-rotation history.
- `GET /api/analytics/benchmarks` returns `available`, `reportName`, `message`, and the actual validated rows: `workload`, `tree`, `resourceCount`, `searchCount`, `heightAfterMetrics`, `avgComparisons`, `avgDepth`, `avgRotationsPerSearch`, and `medianSearchTimeMs` (milliseconds). Handle unavailable/malformed data honestly; keep this synthetic report separate from live access analytics.
- Resource writes use the inspected DTO: positive integer `id`; required title (160 characters max), category and resource type (80 each); optional description (4000), subject (120), academic term (80), absolute HTTP(S) `resourceUrl` (2048), opaque `resourceReference` (2048), and up to 30 tags (48 each). A resource reference is metadata only and must not be opened as a filesystem path. API errors use `{code, message, details, timestamp, searchMetrics}` with the actual 400/404/409/503 behaviors documented in `docs/API.md`.

Centralize these operations in typed request/response definitions and one API client. The prominent name-search input supports partial/case-insensitive metadata search, debounce or explicit submit, clear-search, labelled keyboard-accessible result selection, and distinct loading, empty, retryable error and success states. Use request caching/deduplication, stale-data refresh and mutation invalidation; show validation and not-found feedback. Preserve form input after failed writes and prevent duplicate submits. Use same-origin `/api` requests in Preview/production; allow `VITE_API_BASE_URL` to override this for local setups.

## Application routes and behavior

Implement actual, navigable pages for Dashboard (`/`), Resource Library (`/resources`), Popular Resources (`/popular`), Recent Resources (`/recent`), DSA Visualization (`/dsa`), and Benchmark Analytics (`/benchmarks`). Add working resource creation (`/resources/new`), details (`/resources/:id`) and editing (`/resources/:id/edit`) routes. Use a static `/manus-routes.json` manifest that lists the implemented route patterns and titles, excludes API/assets/404 routes, and is served by the Vite Preview app.

The Dashboard uses the real analytics summary and offers name-based resource search and direct popular/recent links. Do not create trends, growth percentages, unique-user counts, or category-distribution charts not supplied by the API. The Library uses backend pagination, supported category/type filters and supported sorts; show complete returned metadata and persisted PDF attachment counts; allow create/edit/delete with field-level validation and delete confirmation. External URLs are clearly labelled and opened safely. Keep external URL/reference metadata distinct from uploaded PDFs, and explain when a resource has no URL or no attached PDFs. After successful CRUD/access/attachment mutations, refresh affected cached lists, attachment counts and summary data.

Popular and Recent pages use their dedicated endpoints and honest labels; selecting a resource name opens its detail route, triggering the genuine backend ID access. The DSA page renders the API's actual node graph and resource associations where available, highlights root/last accessed node, displays available metrics, refreshes after successful opens and remains navigable for large trees. Its ordinary user path is name-based search/selection. Include a small, clearly labelled optional `DSA Demonstration` input for manual ID lookup, only as an educational presentation control. Include concise, accurate Splay Tree teaching notes; do not claim every lookup beats AVL or depict an invented historical animation. Benchmark Analytics uses Recharts for meaningful elapsed-time and algorithmic-metric comparisons, explicit units, clear workload selection/tooltips and a precise data table, plus workload explanations and honest BST/AVL/Splay behavior.

## Frontend and serving architecture

Keep frontend source in `frontend/` with a clear split among API types/client/hooks, shared app shell/components including a reusable `DocumentAttachments` manager, six navigation pages and resource forms/details, styles/tokens, and tests. Use React Router, TanStack Query (or an equivalently lightweight cache), Recharts, Lucide React, and Vitest with React Testing Library/user-event/jsdom. Use the browser's native PDF renderer inside an accessible embedded viewer; use an upload client capable of reporting `XMLHttpRequest.upload` progress. Use CSS variables, semantic HTML, labels, keyboard focus and `prefers-reduced-motion`; no external APIs or decorative stock imagery.

Pin Node/pnpm using the available Node 22.13.0 and pnpm 11.25.0. Add the pnpm 11 workspace `allowBuilds` policy before installation and allow only the required build scripts after review. Check in the lockfile. Add `.env.example` and document `VITE_API_BASE_URL` plus the local dev default `http://localhost:3000/api`.

For local/Webdev Preview, run Vite on the existing configured Preview port 3000 and proxy `/api` to Spring Boot at port 8080. Use a per-process `PORT=8080` override for that local two-process workflow only; preserve the existing `application.properties` defaults, backend default port 3000, `runtime.port=3000`, API and health contract. Add only the new attachment directory/size settings and do not change existing DB, CSV or port defaults. Keep Preview requests same-origin/relative and preserve `APP_DB_PATH` and all existing rows. Keep the existing Dockerfile and Spring packaging API-only in this phase; do not add SPA fallback or embed the frontend in the backend by default. Any future single-container UI embedding must be an optional, separate deployment choice, not a requirement for development or Preview. Document both startup commands and the hosted SQLite/filesystem durability limitation. Do not publish or deploy this phase.
